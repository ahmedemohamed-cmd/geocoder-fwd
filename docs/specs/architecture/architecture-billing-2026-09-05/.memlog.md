- (direction) Brownfield derive-from-code, fast path, same deliverables as the geocoder run (spine + solution design). Run folder scoped to the domain because the configured run_folder_pattern would collide with the geocoder run on the same date.
- (constraint) VERIFIED: billing/ imports nothing from services/ or shared/. One deliberate duplication, documented in main.py: a local redis client copy isolated by config.REDIS_PREFIX, kept so billing stays an independent deployable.
- (decision) Two planes. The control plane (FastAPI) is a MANAGEMENT plane: it projects key/plan/quota state into APISIX via the Admin API and hosts the /internal/usage sink. It is never in the request path. APISIX + etcd is the data plane and enforces inline.
- (decision) Postgres rollups are the durable source of truth for usage — for billing AND for the tenant-facing display. Redis is a counting and buffering tier only. Learned the hard way: the shared Redis is non-persistent and LRU, so live counters reset on eviction and could not back a usage display.
- (decision) Quota enforcement is cluster-wide and inline via APISIX limit-count(redis), with the Redis key scoped to the calendar period (<group>:<YYYY-MM>) so the quota resets in step with the Postgres rollups. The aggregator re-projects each tenant's consumer-group on month rollover.
- (decision) A rejected request never bills. RPS rejection happens before the quota increment, and incr_tenant_if_allowed is an atomic conditional increment — a request that would exceed the allowance is refused without consuming it.
- (decision) API keys are stored twice by design: sha256 hash for lookup, plus a Fernet-encrypted key_enc so the owning tenant can reveal/copy. Plaintext is never persisted and is unrecoverable from the hash alone.
- (decision) Deletion is soft everywhere: status='deleted' with the row retained for audit. Tenant deletion cascades to its keys in one transaction.
- (decision) Credit units are integer milli-credits end to end (1 credit = 1000) so counters never go floating point. Endpoint attribution is the FIRST PATH SEGMENT, so deep/forward and deep/nearby both bill as 'deep'. Unweighted endpoints cost 1 credit.
- (decision) Identity has two interchangeable verifiers behind one Identity shape, selected by BILLING_AUTH_MODE: 'dev' (local HS256 issuer + users table + PBKDF2) and 'zitadel' (OIDC RS256 against the Zitadel JWKS). Control plane and gateway are auth-mode agnostic by construction.
- (decision) Invoicing is idempotent per (tenant, period): re-running a closed period updates the existing invoice rather than issuing a second one.
- (decision) Free endpoints (health, status, capability discovery) are excluded at the route level from BOTH limit-count and http-logger, so they neither consume quota nor ship usage events.
- (question) billing/gateway.py's module docstring calls itself 'the metered data plane — the distributed enforcement tier', but it is NOT deployed: compose runs APISIX, and main.py builds gateway_app without any service using it. The README is correct, the docstring is stale. Same class of drift as traffic_writer's. Gap-register item.
- (question) BILLING_AUTH_MODE defaults to 'dev' in code but 'zitadel' in compose, and dev mode ships a hardcoded default JWT secret. Running the control plane outside compose silently selects the weaker verifier. Gap-register item, security-relevant.
